# 交付管线部署与飞书集成方案

## 一、当前架构

应用由 React/Vite 前端、NestJS API、MongoDB 和 Redis 组成。MongoDB 保存台账、变更日志、登录用户、字段偏好、导入批次和通知结果；Redis 负责新需求、状态变更、关注人变更和同步事件的可靠消费，失败事件最多重试 3 次后进入死信队列。未配置 MongoDB 或 Redis 时，本地开发可降级使用 JSON 和禁用队列，但测试、预发和生产环境必须连接真实服务。

飞书 OAuth 登录后会自动创建或更新企业用户。所有用户都具有需求方能力，交付管理员和超级管理员是可叠加权限，因此管理员也能切换到“我的需求”工作台。PM 不是全局账号角色，而是需求方提交每条需求时可选的人员字段；被指定的 PM 只看到与自己相关的需求。

## 二、已实现功能

- 需求方通过飞书 OAuth 登录、提交需求、选择多名需求人和关注人、按需指定 PM、查看与下载本人相关需求。
- 需求负责人可继续维护关注人，完成后的需求可评价；超过设定天数未评价时系统自动记为 5 分好评。
- 管理员按负责人字段进入各自视图，超级管理员查看完整台账；每名管理员可在显示区和隐藏区之间拖拽词条、调整顺序，并固定最多 4 个常用列。
- 超级管理员可在“管理员审批”中查找已通过飞书登录的企业成员，直接任命或撤销交付管理员；普通管理员不能管理他人权限，审批动作会写入审计日志。
- 提需求表、数据团队总表和总台账支持 `.xlsx` 预检后增量导入，并记录新增、更新、未变化和冲突数量。
- 系统读取飞书 Base 的提需求表、数据团队总表和总台账：服务启动后立即同步，之后默认每 5 分钟按业务主键增量合并，也可由超级管理员手动触发。三个来源按“提需求表 → 数据团队总表 → 总台账”合并，使总台账成为同名非空字段的最终权威来源。
- 新需求、状态或字段变更、关注人变更会进入 Redis 队列，并通过飞书应用机器人通知需求负责人、需求人、关注人、PM、对接人和方案负责人。
- `/healthz` 提供依赖状态，`/metrics` 提供 Prometheus 文本指标。

飞书 Bot 的技术链路为：NestJS 在需求提交或台账变更时生成事件，`ioredis` 将事件写入 Redis 可靠队列；后台消费者解析台账中的需求负责人、需求人、关注人、PM、对接人和方案负责人，通过 MongoDB 已登录用户映射或飞书通讯录 OpenAPI 得到 `open_id`，再调用飞书 IM OpenAPI 发送应用机器人消息。发送结果写入 MongoDB，失败最多重试 3 次，仍失败则进入 Redis 死信队列；`LARK_WEBHOOK_URL` 可额外发送群机器人通知。

## 三、功能改进与技术栈

| 功能 | 当前实现 | 技术栈 |
| --- | --- | --- |
| 三张飞书表同步与在线入口 | 服务启动时立即读取提需求表、数据团队总表和总台账，之后默认每 5 分钟自动增量合并；管理员可查看在线表链接、同步启用状态与最近同步时间，超级管理员可手动同步。当前属于分钟级自动同步，不是飞书事件 Webhook 的毫秒级实时同步。 | NestJS 同步服务、飞书 Base OpenAPI、业务主键增量合并、MongoDB 持久化、Redis 变更事件 |
| 飞书 Bot 通知 | 新需求和关键字段变更写入可靠队列，后台消费者解析接收人并发送飞书应用机器人消息，失败重试后进入死信队列。 | NestJS、`ioredis`、Redis、飞书通讯录与 IM OpenAPI、MongoDB 通知日志 |
| 需求方与管理员登录 | 飞书 OAuth 回调后自动创建或更新内部用户，未配置管理员角色的员工默认进入需求方页面；管理员只有从管理员入口登录时才进入对应工作台，同一账号可以同时拥有需求方能力。 | 飞书 OAuth 2.0、NestJS、签名 `HttpOnly` 会话 Cookie、MongoDB 用户表、基于 `open_id`/邮箱的角色白名单 |

## 四、部署环境变量

必须配置：

```env
NODE_ENV=production
HOST=0.0.0.0
PORT=5173
AUTH_SECRET=<随机长密钥>
AUTH_MOCK_ENABLED=false

MONGODB_URI=mongodb://<用户名>:<密码>@<MongoDB地址>:27017/delivery_pipeline?authSource=admin
MONGODB_DB=delivery_pipeline
REDIS_URL=redis://:<密码>@<Redis地址>:6379/0
PUBLIC_APP_URL=https://data-panel-dev.shlab.tech

LARK_APP_ID=<飞书应用 App ID>
LARK_APP_SECRET=<通过安全渠道配置>
LARK_REDIRECT_URI=https://data-panel-dev.shlab.tech/api/auth/lark/callback
LARK_AUTH_HOST=https://open.feishu.cn
LARK_API_HOST=https://open.feishu.cn

LARK_WIKI_NODE_TOKEN=<承载台账 Base 的 Wiki 节点 token>
LARK_BASE_WEB_URL=https://aicarrier.feishu.cn/wiki/ZqC3whTTXiU2rUkLdRycTtmhnYE
LARK_LEDGER_TABLE_ID=tbl7FrAYMpseNuPA
LARK_LEDGER_VIEW_ID=vewkBG8gpp
LARK_REQUEST_TABLE_ID=tblrdV8pbi1Ny9mJ
LARK_REQUEST_VIEW_ID=vewFenv6xd
LARK_DATA_TEAM_TABLE_ID=<数据团队总表 table id>
LARK_DATA_TEAM_VIEW_ID=<数据团队总表 view id，可留空>
LARK_SYNC_INTERVAL_MS=300000

LARK_SUPER_ADMIN_OPEN_IDS=<超级管理员 open_id，逗号分隔>
LARK_DELIVERY_ADMIN_OPEN_IDS=<交付管理员 open_id，逗号分隔>
```

如果部署人已经取得 Base 的真实 `app_token`，可设置 `LARK_BASE_TOKEN` 并不设置 `LARK_WIKI_NODE_TOKEN`。否则服务会使用 Wiki API 自动把 `LARK_WIKI_NODE_TOKEN` 解析为 Base `app_token`。若某张表不在同一个 Base 中，可用 `LARK_LEDGER_URL`、`LARK_REQUEST_URL` 或 `LARK_DATA_TEAM_URL` 覆盖对应在线入口。

可选配置：

```env
SATISFACTION_AUTO_GOOD_DAYS=7
LARK_WEBHOOK_URL=<可选的群机器人 webhook>
LARK_SUPER_ADMIN_EMAILS=<超级管理员邮箱，逗号分隔>
LARK_DELIVERY_ADMIN_EMAILS=<交付管理员邮箱，逗号分隔>
```

`ADMIN_PASSWORD` 只用于 `AUTH_MOCK_ENABLED=true` 的本地开发兜底，正式环境不应开放口令管理员登录。密钥、数据库密码和真实数据不得提交到 Git。

## 五、飞书后台配置

飞书应用需要启用网页应用和机器人，并配置与 `LARK_REDIRECT_URI` 完全一致的 OAuth 重定向 URL。应用可用范围需要覆盖全部测试用户和管理员。

应用权限至少包括：用户身份信息、通讯录用户搜索或读取、机器人以应用身份发消息、知识库节点读取，以及多维表格记录读取。权限新增后需要发布新版本，并由企业管理员完成审批；Base 和 Wiki 空间本身也要把该应用加入可访问范围。

管理员身份以 open_id 或企业邮箱配置。超级管理员和交付管理员登录同一个账号后，可以在“管理员视图”和“我的需求”之间切换。超级管理员还可以在页面的“管理员审批”中给已经登录过、已写入 MongoDB 的用户增加或撤销交付管理员权限；超级管理员身份仍只通过部署环境配置。

## 六、发布与验证

开发阶段只推送 `dev`，由 GitLab CI/GitOps 部署到测试域名。验证 OAuth、个人需求隔离、管理员字段权限、PM 可见性、Excel 预检导入、Base 同步、飞书通知和满意度后，再将 `dev` 合并到 `main`。

部署后检查：

```bash
curl https://data-panel-dev.shlab.tech/healthz
curl https://data-panel-dev.shlab.tech/metrics
```

`/healthz` 中 MongoDB、Redis 应为 `ready`，`larkSync` 应为 `configured`。上线前还应检查应用日志中没有 OAuth 回调、Base 权限或机器人发消息错误，并确认 Redis processing 和 dead-letter 队列为空。
