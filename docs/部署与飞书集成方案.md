# 交付管线部署与飞书集成方案

## 一、当前架构

应用由 React/Vite 前端、NestJS API、MongoDB 和 Redis 组成。MongoDB 保存台账、变更日志、登录用户、字段偏好、导入批次和通知结果；Redis 负责新需求、状态变更、关注人变更和同步事件的可靠消费，失败事件最多重试 3 次后进入死信队列。未配置 MongoDB 或 Redis 时，本地开发可降级使用 JSON 和禁用队列，但测试、预发和生产环境必须连接真实服务。

飞书 OAuth 登录后会自动创建或更新企业用户。只有从需求方入口登录过的成员才获得需求方身份；交付管理员和超级管理员是可叠加权限，因此管理员也可以在建立需求方身份后切换到“我的需求”工作台。PM 不是全局账号角色，而是需求方提交每条需求时可选的人员字段；被指定的 PM 只看到与自己相关的需求。

## 二、已实现功能

- 需求方通过飞书 OAuth 登录、提交需求、选择多名需求人和关注人、按需指定 PM、查看与下载本人相关需求。
- 需求负责人可继续维护关注人，完成后的需求可评价；关闭评价或超过设定天数未评价时系统自动记为 5 分好评，1–3 星必须填写理由。
- 所有交付管理员均可查看完整台账；每名管理员可独立隐藏、显示、排序和筛选词条，并选择任意数量的常用词条组成个人视图。
- 超级管理员可在“管理员设置”中直接搜索飞书通讯录并任命或移除交付管理员；普通管理员不能管理他人权限，任命动作会写入审计日志。
- 需求方与管理员身份独立：只有从需求方入口完成登录的成员才获得需求方身份；管理员如需提交或关注自己的需求，需要再从需求方入口登录一次。
- 总台账、245 和高峰加入支持 `.xlsx` 预检后增量导入，并记录新增、更新、未变化和冲突数量。
- 系统读取飞书 Base 的总台账、245 和高峰加入三张业务表：Base 记录新增或修改后由自动化调用受保护的 webhook，系统约 300ms 合并同表连续事件，然后**只按事件携带的 `recordId` 读取那几条记录**并单条 upsert 落库，不再重写整表；服务启动和默认每 5 分钟的全表同步作为漏事件校准，也可由超级管理员手动触发。
- 台账页面每 3 秒轮询 `/api/data/version` 这个写入计数器，计数变化时才重新拉取数据，因此在飞书里改完记录后页面会自行刷新，无需手动重载；页面隐藏或有弹窗打开时暂停轮询。
- 只有“获取状态”发生真实变化时才进入通知队列，并通过飞书应用机器人通知需求负责人、需求人、关注人、PM，以及该需求相关且已被任命的管理员。
- 交付效率分析按 Excel 口径计算六个交付环节的 Q1/Q2 样本数、平均值、中位数、标准差、效率提升，以及预计与实际交付偏差和数据来源对比。
- `/healthz` 提供依赖状态，`/metrics` 提供 Prometheus 文本指标。

飞书 Bot 的技术链路为：NestJS 在需求提交、网页台账更新或三张飞书表同步时比较“获取状态”，仅为真实状态变化生成事件，`ioredis` 将事件写入 Redis 可靠队列；后台消费者把需求负责人、需求人、关注人和 PM 识别为需求方，把部门负责人、项目对接人、解决方案负责人和承接方责任人中已任命的管理员识别为负责管理员，通过 MongoDB 已登录用户映射或飞书通讯录 OpenAPI 得到 `open_id`，再使用 `LARK_APP_ID` 对应的“交付管线”应用机器人调用飞书 IM OpenAPI 发送个人通知。消息包含需求名称、原状态、新状态、Sprint 和系统入口；首次全量导入不发送历史状态通知，避免批量打扰。发送结果写入 MongoDB，失败最多重试 3 次，仍失败则进入 Redis 死信队列；`LARK_WEBHOOK_URL` 仅在需要额外发送群通知时配置。

## 五、飞书后台配置

飞书应用需要启用网页应用和机器人，并配置与 `LARK_REDIRECT_URI` 完全一致的 OAuth 重定向 URL。应用可用范围需要覆盖全部测试用户和管理员。

应用权限分为两类身份，不能互相替代。后端服务全部使用 `tenant_access_token`（应用身份），`npm run setup:lark-sync` 使用 `lark-cli` 的用户身份。

应用身份（后端运行时必需）：

| 权限 | 用途 | 对应接口 |
| --- | --- | --- |
| `auth:user.id:read` | OAuth 登录并获取当前用户身份 | `authen/v1/user_info`、`authen/v2/oauth/token` |
| `contact:contact.base:readonly` | 读取通讯录成员基本信息 | `contact/v3/users/find_by_department` |
| `contact:user.base:readonly` | 读取成员姓名与 `open_id` | `contact/v3/users/find_by_department` |
| `contact:department.base:readonly` | 读取部门树，用于通讯录选人 | `contact/v3/departments/0/children` |
| `im:message:send_as_bot` | 状态变化时发送机器人通知 | `im/v1/messages` |
| `wiki:node:read` | 把 Wiki 节点解析为 Base `app_token` | `wiki/v2/spaces/get_node` |
| `base:table:read` | 读取三张业务表的表结构与名称 | `bitable/v1/apps/{app_token}/tables` |
| `base:record:retrieve` | **实时同步读取单条记录** | `bitable/v1/apps/{app_token}/tables/{table_id}/records/{record_id}` |
| `bitable:app:readonly` | **兜底全量同步分页读取记录** | `bitable/v1/apps/{app_token}/tables/{table_id}/records` |

用户身份（仅 `npm run setup:lark-sync` 需要）：`base:workflow:read`、`base:workflow:create`、`base:workflow:update`、`base:table:read`。

`base:record:read` 是用户身份权限，不能替代后端 `tenant_access_token` 所需的应用身份权限。飞书的报错文案会把 `base:record:retrieve`、`bitable:app:readonly`、`bitable:app` 三者并列成「任一即可」，但 2026-07-29 实测证明**它们对分页列表接口并不等价**：只开 `base:record:retrieve` 时单条 `records/{record_id}` 返回 `code=0`，而分页 `records` 和 `records/search` 仍返回 `99991672`。因此两项都要开：前者支撑实时同步，后者支撑兜底全量同步。权限新增后需要发布新版本并由企业管理员审批。

Base 和 Wiki 空间本身也要把该应用加入可访问范围。若 Base 开启了高级权限，还必须逐张表把应用角色的可访问范围放开——只授权应用访问 Base 不等于授权访问其中每张表，未授权的表会在 `tables` 清单里直接消失，单记录读取返回 `1254302 RolePermNotAllow`。

用应用凭证可以直接实测每项权限是否已生效，不必依赖后台界面：

```bash
# 返回 code=0 表示该权限已开通；99991672 表示尚未开通并会列出缺失的 scope
curl -s -X POST "$LARK_API_HOST/open-apis/auth/v3/tenant_access_token/internal" \
  -H 'Content-Type: application/json' \
  -d "{\"app_id\":\"$LARK_APP_ID\",\"app_secret\":\"$LARK_APP_SECRET\"}"
curl -s -H "Authorization: Bearer <tenant_access_token>" \
  "$LARK_API_HOST/open-apis/bitable/v1/apps/<app_token>/tables/$LARK_LEDGER_TABLE_ID/records?page_size=1"
```

`/healthz` 的 `larkSyncStatus.sources[].lastError` 也会逐张表回显飞书原始报错和开通链接。

部署环境配置完 `PUBLIC_APP_URL` 和 `LARK_BASE_WEBHOOK_SECRET` 后，在具备 Base 管理权限且已登录 `lark-cli` 的管理终端执行：

```bash
npm run setup:lark-sync
```

脚本会读取三张真实数据表的名称，创建并启用“交付管线实时同步 · 总台账 / 245 / 高峰加入”三个 Workflow；重复执行时会复用同名 Workflow，不会重复创建。应用身份还需要被授予该 Base 的查看权限，否则运行时会返回 `91403`。

管理员身份可通过 open_id、企业邮箱或姓名初始化。超级管理员还可以在页面的“管理员设置”中直接从飞书通讯录任命管理员；超级管理员身份仍只通过部署环境配置。管理员只有在从需求方入口完成过登录后，才会同时拥有需求方工作台。

两类角色的权威来源不同，这决定了改配置后会不会生效：

- **`delivery_admin` 以 MongoDB 为准。** `LARK_DELIVERY_ADMIN_OPEN_IDS`、`LARK_DELIVERY_ADMIN_EMAILS` 和 `LARK_DELIVERY_ADMIN_NAMES` 只在用户**首次登录**时用于初始化。之后超级管理员在页面上移除某人的管理员权限，即使姓名仍在 `LARK_DELIVERY_ADMIN_NAMES` 里，也不会在下次登录时被恢复。
- **`super_admin` 以部署环境为准。** 页面明确拒绝新增超级管理员，也拒绝移除，所以环境变量是唯一途径。把 open_id 加入 `LARK_SUPER_ADMIN_OPEN_IDS` 后，即使该用户早已登录过，下次登录也会拿到超级管理员权限。

会话不再只信 Cookie 里的角色：每次请求都会用 `open_id` 回查 MongoDB 的当前角色，所以撤销权限立即生效，不需要等 8 小时会话过期。MongoDB 不可用时回退到 Cookie 中的角色，避免数据库抖动把所有人挡在外面。

与 07-29 相比只有一项变化，但那一项很关键：**用户身份的高级权限阻塞已解除**，`lark-cli base +workflow-list` 现在能读到该 Base 的 26 个 Workflow（其中没有任何“交付管线实时同步”，所以不能复用）。`800004011 not advanced base owner` 不再出现，三个 Workflow 具备创建条件。

仍未解除的两项：

1. **应用身份缺列表类权限。** `bitable:app:readonly`（或 `bitable:app`）尚未生效，分页 `records`、`records/search`、`fields` 三个接口全部 `99991672`。已开通的 `base:record:retrieve` 实测只放行单条读取，两者不等价。后果是**实时同步对总台账和 245 可用，但启动同步和 5 分钟兜底全量拉不到任何记录**——一旦漏事件就永久漏数据。开通入口：`https://open.feishu.cn/app/cli_aacc8ff785fadce7/auth?q=bitable:app:readonly&op_from=openapi&token_type=tenant`，开通后需发布新版本并由企业管理员审批。
2. **高峰项目获取表未授权给应用。** `tbl8iFcCizgi0YrU` 用用户身份可读（62 列、142 条），但应用身份的 `tables` 清单里没有它。该 Base 开启了高级权限，应用角色只覆盖“数据团队总表”和“245获取表”。这属于 Base 资源授权，重新申请应用 scope 无效，需要在 Base 高级权限里把该表加入应用“交付管线”（App ID `cli_aacc8ff785fadce7`）所在角色。

创建 Workflow 前必须先把部署环境的 `PUBLIC_APP_URL` 设为 `https://data-panel-dev.shlab.tech`。`npm run setup:lark-sync` 现在会在写入任何东西之前校验回调地址：非 `https`、或指向 `localhost`/`127.*`/`10.*`/`192.168.*`/`172.16-31.*`/`169.254.*`/`.local`/`.internal` 时直接终止，避免在共享 Base 里留下飞书访问不到的死回调。本地 `.env` 的 `http://127.0.0.1:5173` 会被这条校验拦下。

通讯录搜索和 Bot 通知属于独立的应用能力，不影响三表读取；需要时再按审批优先级补充验证。

### 通知基线（按表独立）

全量同步把某张表的第一次成功读取当作基线，只落库不发通知，避免部署或重启把历史状态差异重播成一批通知。基线**按表独立记录**，而不是一个全局开关：当前高峰表长期读不到，如果基线是全局的，另两张表成功后就会把它一并标记为已就绪，等高峰权限补齐时它的首次成功同步会把 142 条历史差异全部推送出去。`/healthz` 的 `larkSyncStatus.sources[].notificationBaseline` 逐表回显基线状态，`notificationBaselineReady` 仅在全部已配置的表都建立基线后才为 `true`。

Webhook 单记录路径**不受基线约束**：一个事件只碰一条记录，不存在批量打扰的风险，而且事件本身就说明有人刚改过这条记录。

### 实时同步链路实测（2026-07-29，应用身份）

本地以隔离的 `DATA_DIR` 起服务，用真实 `record_id` 打 `/api/webhooks/lark/base`，全链路已跑通：

| 场景 | 结果 |
| --- | --- |
| 1 条记录事件 | 端到端 **3.65 秒** 落库，批次 `total=1 更新=1` |
| 同窗口 5 条记录事件 | 端到端 **4.60 秒** 落库，批次 `total=5 更新=5`，台账仍 467 条（全部正确匹配，无重复插入） |
| 错误签名 / 未知表 | `401` / `400` |
| 单记录读取失败 | 自动降级为该表全量同步，事件不丢 |

耗时构成（实测中位数）：300ms 事件合并窗口 + **飞书单记录接口 2.3 秒** + 存储层单条 upsert 12ms。飞书这个接口本身就比 `tables` 接口（384ms）慢一个数量级，是延迟的主要来源，代码侧无法再压缩。因此**做得到「几秒级」，做不到「1 秒内」**：加上前端 3 秒轮询，用户从在 Base 里改完到页面刷新约 4～7 秒。

同窗口内的多条记录改为并发读取（每批 5 条，避免触发限流），只有合并落库保持串行——串行读取时 5 条要 0.3 + 5×2.3 ≈ 11.8 秒，并发后与单条基本持平。

存储层单条 upsert 已按业务键验证：命中同一 `任务代码` 时更新而非新增、完全相同的重复推送判为 `unchanged` 不触发写入、新字段自动并入字段表、键里含零宽空格（`U+200B`）仍正确命中同一条、无 `任务代码` 时回退到 `项目名称`。

| --- | --- | --- | --- | --- | --- | --- |
| 合并前台账 | 467 | — | — | — | — | 467 |
| 总台账 | 623 | 163 | 460 | 0 | 110 | 630 |
| 245 | 4586 | 4552 | 34 | 0 | 33 | 5182 |

字段数由 48 增至 73。三张表都是需求粒度、字段高度重叠（总台账 40 列、245 共 54 列、高峰加入 43 列），因此可以合并进统一台账。

三点需要在正式同步前确认：

- **245 表体量决定台账规模**。它的 4586 条中大量是自动采集线索（`数据ID` 形如 `xsk_202505000316`、`获取渠道` 为“自动采集”），且多数没有 `任务代码`，业务键会回退到 `项目名称`。首次全量同步后台账将从 467 条增至 5259 条，是原来的 11 倍。若 245 只应同步其中一部分，应为它单独配置一个过滤视图并改用该 `view_id`，而不是同步整表。
- **`未变化` 为 0 属正常**。当前 `data/project-data.json` 里的数据早于飞书现状，350 条更新记录都存在真实字段差异，不是 `数据来源` 字段被重算造成的假更新。
- **首次同步会入队 36 条状态变化通知**，全部是真实的“获取状态”变化（例如`采购调研中`→`供应商选择中`），零宽字符导致的误报为 0 条。`performSync` 的 `notifyStatusChanges` 只在台账为空时才关闭通知，而线上台账非空，所以这 36 条会真实推送给相关人员。如果不希望这批历史差异触达用户，应在首次全量同步时临时关闭通知消费者。

飞书 Base 的文本里含零宽空格（`U+200B`），例如`解决方案中​`。业务键匹配走 `normalizeText` 已经清理该字符，但 `enqueueStatusChanges` 的状态比较只做 `.trim()`。当前两侧数据同源所以无影响；若今后把不含零宽字符的 Excel 数据与飞书数据混用，会产生整批状态变化误报。
