# 交付管线部署与飞书集成方案

## 一、当前架构

应用由 React/Vite 前端、NestJS API、MongoDB 和 Redis 组成。MongoDB 保存台账、变更日志、登录用户、字段偏好、导入批次和通知结果；Redis 负责新需求、状态变更、关注人变更和同步事件的可靠消费，失败事件最多重试 3 次后进入死信队列。未配置 MongoDB 或 Redis 时，本地开发可降级使用 JSON 和禁用队列，但测试、预发和生产环境必须连接真实服务。

飞书 OAuth 登录后会自动创建或更新企业用户。只有从需求方入口登录过的成员才获得需求方身份；交付管理员和超级管理员是可叠加权限，因此管理员也可以在建立需求方身份后切换到“我的需求”工作台。PM 不是全局账号角色，而是需求方提交每条需求时可选的人员字段；被指定的 PM 只看到与自己相关的需求。

## 二、已实现功能

- 需求方既可以在本系统提交需求，也可以直接打开飞书需求表单（`LARK_REQUEST_FORM_URL`）填写；表单写入数据团队需求池，最长一个同步周期（默认 5 分钟）后出现在“我的需求”。未配置该变量时入口自动隐藏。
- 需求方通过飞书 OAuth 登录、提交需求、选择多名需求人和关注人、按需指定 PM、查看与下载本人相关需求。
- 需求负责人可继续维护关注人，完成后的需求可评价；关闭评价或超过设定天数未评价时系统自动记为 5 分好评，1–3 星必须填写理由。
- 所有交付管理员均可查看完整台账；每名管理员可独立隐藏、显示、排序和筛选词条，并选择任意数量的常用词条组成个人视图。
- 超级管理员可在“管理员设置”中直接搜索飞书通讯录并任命或移除交付管理员；普通管理员不能管理他人权限，任命动作会写入审计日志。
- 需求方与管理员身份独立：只有从需求方入口完成登录的成员才获得需求方身份；管理员如需提交或关注自己的需求，需要再从需求方入口登录一次。
- 四张同步源表都支持 `.xlsx` 预检后增量导入，并记录新增、更新、未变化和冲突数量；导入时选择的来源名与同步来源名统一为飞书表名，旧标签（`总台账`、`245`、`高峰加入`）仍作为输入被接受。
- 系统读取飞书 Base 的数据团队需求池、战略语料库获取表、高峰项目获取表、数据团队总表四张业务表：Base 记录新增或修改后由自动化调用受保护的 webhook，系统约 300ms 合并同表连续事件，然后**只按事件携带的 `recordId` 读取那几条记录**并单条 upsert 落库，不再重写整表；服务启动和默认每 5 分钟的全表同步作为漏事件校准，也可由超级管理员手动触发。
- 台账页面每 3 秒轮询 `/api/data/version` 这个写入计数器，计数变化时才重新拉取数据，因此在飞书里改完记录后页面会自行刷新，无需手动重载；页面隐藏或有弹窗打开时暂停轮询。
- 只有“获取状态”发生真实变化时才进入通知队列，并通过飞书应用机器人通知需求负责人、需求人、关注人、PM，以及该需求相关且已被任命的管理员。
- 交付效率分析按 Excel 口径计算六个交付环节的 Q1/Q2 样本数、平均值、中位数、标准差、效率提升，以及预计与实际交付偏差和数据来源对比。
- `/healthz` 提供依赖状态，`/metrics` 提供 Prometheus 文本指标。

飞书 Bot 的技术链路为：NestJS 在需求提交、网页台账更新或四张飞书表同步时比较“获取状态”，仅为真实状态变化生成事件，`ioredis` 将事件写入 Redis 可靠队列；后台消费者把需求负责人、需求人、关注人和 PM 识别为需求方，把部门负责人、项目对接人、解决方案负责人和承接方责任人中已任命的管理员识别为负责管理员，通过 MongoDB 已登录用户映射或飞书通讯录 OpenAPI 得到 `open_id`，再使用 `LARK_APP_ID` 对应的“交付管线”应用机器人调用飞书 IM OpenAPI 发送个人通知。消息包含需求名称、原状态、新状态、Sprint 和系统入口；首次全量导入不发送历史状态通知，避免批量打扰。发送结果写入 MongoDB，失败最多重试 3 次，仍失败则进入 Redis 死信队列；`LARK_WEBHOOK_URL` 仅在需要额外发送群通知时配置。

### 同步哪几张表：最小表集的度量结论

这个 Base 里应用可见 33 张表。同步表数不是越多越好——`mergeFields` 是「非空覆盖」的最后写入者胜出，多同步一张粒度不对的表会污染整个台账。因此按两个标准逐表实测过：**是不是需求粒度**，以及**是不是独家携带某些信息**。

结论：**三张是满足全部产品目标的最小集，四张是严格无损**。

| 同步来源 | 条数 | 独有需求数 | 独家携带的信息 | 为什么不能省 |
| --- | --- | --- | --- | --- |
| 数据团队需求池 | 689 | 312 | `需求方` 680 条 / 174 个姓名、`进展状态` 651 条 | **唯一的需求方来源**。没有它，需求方登录后看不到自己的需求，「需求方查看本人进展」这个目标直接落空 |
| 战略语料库获取表 | 4679 | 3917 | `解决方案对接时间` 492 条 | 台账体量的主体；四张表里唯一有方案对接时间的表，交付效率分析的六环节缺一环 |
| 数据团队总表 | 646 | 246 | `项目对接人` 645 条、`实际验收通过时间` 35 条、`计划验收完成时间` 12 条 | 交付进展的权威来源，管理员视图和验收环节都依赖它 |
| 高峰项目获取表 | 142 | 40 | 无 | 严格说可省——它没有任何独家字段。但它已经接好、权限已开、40 条需求是别处没有的，边际成本为零，所以保留 |

同步顺序 **需求池 → 战略语料库 → 高峰 → 总表** 是设计而非巧合。合并是最后写入者胜出，共享列的权威来源必须最后跑：总表拥有交付进展，所以放最后；需求池贡献需求方身份和一个偏摄入侧的 `进展状态`，总表有权覆盖它。改动 `sourceConfigurations()` 里的顺序等于改变谁说了算。

明确排除的表，以及排除的理由（都实测过，不是凭表名判断）：

- **外文语料库总表（22327 条）是陷阱。** 表名像是主表，实际是**明细行粒度**：主键是 `SourceID` + `数据ID`（形如 `xsk_202604022849`），带 `入库地址`、`入库大小(GB)`，没有任何交付阶段时间字段，只有 38 / 22327 条能和现有台账连上。同步进来会把台账淹掉，且一条需求对应上千行明细，业务键会互相覆盖。
- **供应商与结算尾部（外部采集 75、内部采集 98、外部采集-245 1449、外部标注-245 76、供应商评估 58）是多对一。** 一条需求可以有多个供应商报价，last-writer-wins 会**静默把多个供应商压成一行**，看起来有数据、实际是错的。要用这些数据必须先在飞书侧聚合，或者在系统里另建一对多的模型。
- **网络安全（280）、CBRNE（24）是上游摄入表**，没有 `任务代码` 也没有 `项目名称`，在飞书内部已经汇入需求池，重复同步只会产生一批无法连接的孤立行。
- **待澄清项目（76）是唯一还没定的判断题。** 它是第二个 `需求方` 来源（70 条 / 10 个姓名），但**完全没有状态字段**，且 45 / 76 已经被 `任务代码` 覆盖。同步它意味着需求方会看到一条查不到进展的需求，所以暂不纳入，需要业务侧确认后再决定。

### 字段别名（按来源翻译，不改原列）

同一个概念在四张表里叫不同名字，不翻译就会在台账里分裂成两列，业务键和需求方视图各读一半。`src/server/core/source-fields.ts` 按来源做翻译，**只在目标列为空时写入，并且始终保留原列**，所以飞书里看得见的东西不会在台账里消失。

| 来源 | 原列 | 台账规范列 |
| --- | --- | --- |
| 需求池 | `需求描述` / `需求方` / `进展状态` / `提出时间` / `期望交付时间` / `完成日期` / `所属部门` / `学科` / `预算（任务确认对接填写）` | `项目名称` / `需求人` / `获取状态` / `需求提出时间` / `期望交付日期` / `实际交付完成日期` / `隶属部门` / `领域或学科` / `预算金额` |
| 战略语料库 | `内部需求方` / `供应商承诺交付完成时期` / `签收数量（GB）` | `需求人` / `供应商承诺交付日期` / `签收交付量（GB）` |
| 高峰 | `验收通过交付量（GB）` | `验收通过交付量(GB)` |

最后一条是真实存在的全角 / 半角括号分裂：高峰写全角 `（GB）`，总表写半角 `(GB)`，不映射就会永久存在两列同名指标。

两个**看起来该映射、实测不该映射**的：

- `战略语料库.接口人` 与 `总表.项目对接人` 只有 4 / 9 个姓名重合——这是两个不同角色，映射等于凭空指派责任人。
- `需求池.当前状态跟进人员` 与 `总表.内部责任人` 只有 4 / 10 重合，同理。

业务键的偏好差异也量化过：总表偏 `任务代码`（637 / 646），需求池偏 `2026需求编码`，理论上两侧可能各选不同的键。实测受影响的只有 **6 行**（需求池 4、战略语料库 2、高峰 0），所以 `importBusinessKey` 的优先级不动。需求池的 `2026需求编码` 是 689 / 689 满覆盖，不存在回退到组合键的情况。

### 日期字段必须转换（否则会写坏台账）

飞书 Base 把所有日期和时间字段返回为 **epoch 毫秒**。原样落库会把 `需求提出时间`、`期望交付日期` 这些需求方看得见的列变成一串数字。`normalizeBaseFieldValues` 在读取层转成台账既有的 `2026/07/01` 格式，两个条件同时满足才转换：**列名匹配 `时间|日期|时期`**，且**值落在 2000–2100 的 epoch 区间**。第二个条件不能省——`期望交付日期` 在总表里是**文本列**，装着`最大值（待填）`这类人写的内容；第一个条件也不能省，否则数量和金额会被当成时间戳。实测过 17 个日期类列名的全部数值都在 epoch 区间内，且**没有任何非日期类列**含 epoch 区间的数值。

纯日期字段和日期时间字段要用**不同时区**格式化：Base 把纯日期锚定在 **UTC 零点**，日期时间存的是真实瞬时。纯日期用 UTC 读还是当天，用 Asia/Shanghai 读也还是当天；但一个上海傍晚的瞬时用 UTC 读会退回前一天。所以按 `millis % 86400000 === 0` 判断，整日取 UTC、其余取 Asia/Shanghai，否则全部纯日期字段会集体错一天。

### 状态变更比对：整轮一次，不是逐源一次

需求池的 `进展状态` 和总表的 `获取状态` 在 **17 条记录上不一致**。如果按来源逐个比对，同一个同步周期里需求池会写入 X、总表随后覆盖成 Y，比对器会为一个从未真正变化的状态推送通知——**每 5 分钟 17 条，永远不停**。所以比对改为：循环前快照，循环中只累积「本轮被碰过的业务键 → 供给它的来源」，全部来源合并完成后**整轮只比对一次**，只有活过所有来源合并的状态变化才算变化。按表独立的基线语义保持不变，本轮首次成功读取的表不参与比对。

`table_id` 和 `view_id` 就是链接中 `table=` 与 `view=` 后面的值，四组值已经写入 `.env.example`，不需要再从网页复制。战略语料库获取表就是文档旧版里的「245」，只是飞书侧改了表名；`LARK_245_TABLE_ID` / `LARK_245_VIEW_ID` 仍作为 `LARK_CORPUS_*` 的回退被读取，所以老部署不改环境变量也不会指错表。

四个 Base Workflow 分别监听对应表的记录新增和修改，并向 `https://<部署域名>/api/webhooks/lark/base` 发送 JSON；请求头 `X-Lark-Sync-Secret` 必须等于部署环境的 `LARK_BASE_WEBHOOK_SECRET`，请求体为 `{"tableId":"对应 table_id","recordId":"触发记录 ID"}`。

推送事件的是 Base 的**自动化流程（Workflow）**，不是机器人，两者容易混。表格里不需要、也无法通过“创建机器人”来做同步：Base 自动化里的“机器人”动作只能把消息发到群或个人，发不出带自定义请求头的 HTTP 请求，也拿不到 `recordId`。要用的是「记录新增或修改时触发」+「发送 HTTP 请求」这一对动作，`npm run setup:lark-sync` 建的就是它，在 Base 的自动化面板里手工建四条等价流程也可以。本项目里的机器人（应用 `交付管线` 的 Bot）走的是**反方向**：状态变化后由后端用 `im:message:send_as_bot` 主动通知到人，与同步链路无关。

## 五、飞书后台配置

飞书应用需要启用网页应用和机器人，并配置与 `LARK_REDIRECT_URI` 完全一致的 OAuth 重定向 URL。应用可用范围需要覆盖全部测试用户和管理员。

应用权限分为两类身份，不能互相替代。后端服务全部使用 `tenant_access_token`（应用身份），`npm run setup:lark-sync` 使用 `lark-cli` 的用户身份。

应用身份（后端运行时必需）：

| 权限 | 用途 | 对应接口 |
| --- | --- | --- |
| `auth:user.id:read` | OAuth 登录并获取当前用户身份 | `authen/v1/user_info`、`authen/v2/oauth/token` |
| `contact:contact.base:readonly` | 读取通讯录成员基本信息 | `contact/v3/users/find_by_department` |
| `contact:user.base:readonly` | 读取成员姓名与 `open_id` | `contact/v3/users/find_by_department` |
| `contact:department.base:readonly` | 遍历企业部门树，以便从全员通讯录搜索并任命管理员 | `contact/v3/departments/0/children` |
| `im:message:send_as_bot` | 状态变化时发送机器人通知 | `im/v1/messages` |
| `wiki:node:read` | 把 Wiki 节点解析为 Base `app_token` | `wiki/v2/spaces/get_node` |
| `base:table:read` | 读取四张业务表的表结构与名称 | `bitable/v1/apps/{app_token}/tables` |
| `base:record:read` | **实时同步读取单条记录** | `bitable/v1/apps/{app_token}/tables/{table_id}/records/{record_id}` |
| `base:record:retrieve` | **兜底全量同步分页读取记录**（`bitable:app:readonly` 或 `bitable:app` 也可满足） | `bitable/v1/apps/{app_token}/tables/{table_id}/records` |

用户身份（仅 `npm run setup:lark-sync` 需要）：`base:workflow:read`、`base:workflow:create`、`base:workflow:update`、`base:table:read`。

飞书这套 Base 权限的命名与直觉相反，2026-07-30 用 `application/v6/applications/{app_id}` 读该应用的 `scopes` 清单核实过：**`base:record:read` 管单条读取，`base:record:retrieve` 管分页列表**，两者不是「详细 / 概要」的关系。当前清单里有 `base:record:read`（`token_types` 含 `tenant`），所以 `records/{record_id}` 通得过；`base:record:retrieve`、`bitable:app:readonly`、`bitable:app` 三个一个都没有，所以分页 `records` 返回 `99991672`，而这个报错文案恰好把这三者并列成「任一即可」。补开其中任意一个即可，`base:record:retrieve` 是最小授权。权限新增后需要发布新版本并由企业管理员审批。

`base:record:read` 只能用户身份使用的说法不成立——它的 `token_types` 是 `['user', 'tenant']`。反过来 `base:field:read` 的 `token_types` 只有 `user`，所以应用身份读不了 `fields`，但同步代码只调 `tables`、`records` 和 `records/{record_id}`，不读字段定义，因此不影响运行。

Base 和 Wiki 空间本身也要把该应用加入可访问范围。若 Base 开启了高级权限，还必须逐张表把应用角色的可访问范围放开——只授权应用访问 Base 不等于授权访问其中每张表，未授权的表会在 `tables` 清单里直接消失，单记录读取返回 `1254302 RolePermNotAllow`。

用应用凭证可以直接实测每项权限是否已生效，不必依赖后台界面：

```bash
# 返回 code=0 表示该权限已开通；99991672 表示尚未开通并会列出缺失的 scope
curl -s -X POST "$LARK_API_HOST/open-apis/auth/v3/tenant_access_token/internal" \
  -H 'Content-Type: application/json' \
  -d "{\"app_id\":\"$LARK_APP_ID\",\"app_secret\":\"$LARK_APP_SECRET\"}"
curl -s -H "Authorization: Bearer <tenant_access_token>" \
  "$LARK_API_HOST/open-apis/bitable/v1/apps/<app_token>/tables/$LARK_LEDGER_TABLE_ID/records?page_size=1"
```

`/healthz` 的 `larkSyncStatus.sources[].lastError` 也会逐张表回显飞书原始报错和开通链接。

部署环境配置完 `PUBLIC_APP_URL` 和 `LARK_BASE_WEBHOOK_SECRET` 后，在具备 Base 管理权限且已登录 `lark-cli` 的管理终端执行：

```bash
npm run setup:lark-sync
```

脚本会读取四张真实数据表的名称，创建并启用“交付管线实时同步 · 数据团队需求池 / 战略语料库获取表 / 高峰项目获取表 / 数据团队总表”四个 Workflow；重复执行时会复用同名 Workflow，不会重复创建。脚本里的表清单必须和 `sourceConfigurations()` 保持一致——指向服务端不认识的表的 Workflow 会一直收到 400。应用身份还需要被授予该 Base 的查看权限，否则运行时会返回 `91403`。

交付管理员不再通过姓名、邮箱或 open_id 环境变量自动初始化，只能由超级管理员在页面的“管理员设置”中从飞书通讯录任命；超级管理员身份仍只通过部署环境配置。管理员只有在从需求方入口完成过登录后，才会同时拥有需求方工作台。

两类角色的权威来源不同，这决定了改配置后会不会生效：

- **`delivery_admin` 以 MongoDB 为准。** 只有超级管理员的任命与移除操作能改变该角色，重新登录不会从姓名白名单恢复权限。
- **`super_admin` 以部署环境为准。** 页面明确拒绝新增超级管理员，也拒绝移除，所以环境变量是唯一途径。把 open_id 加入 `LARK_SUPER_ADMIN_OPEN_IDS` 后，即使该用户早已登录过，下次登录也会拿到超级管理员权限。

会话不再只信 Cookie 里的角色：每次请求都会用 `open_id` 回查 MongoDB 的当前角色，所以撤销权限立即生效，不需要等 8 小时会话过期。MongoDB 不可用时回退到 Cookie 中的角色，避免数据库抖动把所有人挡在外面。

### 通讯录搜索：为什么会卡，以及搜不到人的两种原因

任命管理员和「飞书选择」人员都走同一个通讯录搜索。飞书**没有**给应用身份提供可用的搜索接口，实测：

| 接口 | 结果 |
| --- | --- |
| `GET /search/v1/user` | `99991663`，只接受**用户身份** token |
| `GET /contact/v3/users/search` | `99992351`，该路径不存在 |
| `POST /contact/v3/users/batch_get_id` | `99991672`，需要 `contact:user.id:readonly`（未开通），且只能按手机 / 邮箱精确查，不能按姓名模糊查 |

所以只能遍历部门再遍历成员，在内存里过滤。这条路的代价实测为：**90 个部门 2 次请求 1.0 秒 + 2058 名成员 118 次请求**。原先每批 6 个部门并发、缓存 5 分钟、且没有 in-flight 去重，后果是一次冷搜索 **33.2 秒 / 120 次飞书请求**，前端只能一直停在「正在搜索…」；连点几次还会并行跑 N 遍全量遍历，互相拖死并触发限流。

现在的做法：

- 并发从 6 提到 20（实测 33.2 秒 → 18.3 秒）。再提到 45 只有 16.0 秒，瓶颈是每个部门内部的串行分页而不是扇出，所以停在 20 以保留限流余量。
- **in-flight 去重**：并发调用共享同一次遍历。三个并发冷搜索合计 23.3 秒，而不是三倍。
- 缓存 5 分钟 → **30 分钟 + stale-while-revalidate**：过期后先返回旧数据、后台刷新，绝不让搜索等一次重建。
- **启动时预热**：服务启动就异步走一遍，正常情况下没有人会撞上冷启动。命中缓存的搜索实测 **1 毫秒**。

「搜不到组织架构外的人」是**飞书侧的数据范围限制，不是代码问题**。`GET /open-apis/contact/v3/scopes` 显示该应用的通讯录权限范围是 **17 个部门 + 1 个成员**，可触达 2058 人；范围外的成员在所有通讯录接口里都不返回，和「查无此人」完全无法区分。代码能做的只是**把边界说出来**：搜索无结果时接口一并返回 `scope`，前端提示「当前应用的通讯录权限范围只覆盖 17 个部门、可见 2058 人，如果对方在范围外，需要在飞书开发者后台扩大通讯录权限范围」。要真正搜到全公司，必须在飞书管理后台扩大该应用的通讯录权限范围。

### 通知基线（按表独立）

全量同步把某张表的第一次成功读取当作基线，只落库不发通知，避免部署或重启把历史状态差异重播成一批通知。基线**按表独立记录**，而不是一个全局开关：高峰表曾经长期读不到，如果基线是全局的，另几张表成功后就会把它一并标记为已就绪，等高峰权限补齐时它的首次成功同步会把 142 条历史差异全部推送出去。四张表的权限现在都已开通，但这个语义要保留——今后新增来源或某张表临时失权时同样适用。`/healthz` 的 `larkSyncStatus.sources[].notificationBaseline` 逐表回显基线状态，`notificationBaselineReady` 仅在全部已配置的表都建立基线后才为 `true`。

Webhook 单记录路径**不受基线约束**：一个事件只碰一条记录，不存在批量打扰的风险，而且事件本身就说明有人刚改过这条记录。

### 实时同步链路实测（2026-07-29，应用身份）

本地以隔离的 `DATA_DIR` 起服务，用真实 `record_id` 打 `/api/webhooks/lark/base`，全链路已跑通：

| 场景 | 结果 |
| --- | --- |
| 1 条记录事件 | 端到端 **3.65 秒** 落库，批次 `total=1 更新=1` |
| 同窗口 5 条记录事件 | 端到端 **4.60 秒** 落库，批次 `total=5 更新=5`，台账仍 467 条（全部正确匹配，无重复插入） |
| 错误签名 / 未知表 | `401` / `400` |
| 单记录读取失败 | 自动降级为该表全量同步，事件不丢 |

耗时构成（实测中位数）：300ms 事件合并窗口 + **飞书单记录接口 2.3 秒** + 存储层单条 upsert 12ms。飞书这个接口本身就比 `tables` 接口（384ms）慢一个数量级，是延迟的主要来源，代码侧无法再压缩。因此**做得到「几秒级」，做不到「1 秒内」**：加上前端 3 秒轮询，用户从在 Base 里改完到页面刷新约 4～7 秒。

同窗口内的多条记录改为并发读取（每批 5 条，避免触发限流），只有合并落库保持串行——串行读取时 5 条要 0.3 + 5×2.3 ≈ 11.8 秒，并发后与单条基本持平。

存储层单条 upsert 已按业务键验证：命中同一 `任务代码` 时更新而非新增、完全相同的重复推送判为 `unchanged` 不触发写入、新字段自动并入字段表、键里含零宽空格（`U+200B`）仍正确命中同一条、无 `任务代码` 时回退到 `项目名称`。
