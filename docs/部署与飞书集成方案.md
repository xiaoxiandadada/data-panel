# 交付管线部署与飞书集成方案

## 一、当前架构

应用由 React/Vite 前端、NestJS API、MongoDB 和 Redis 组成。MongoDB 保存台账、变更日志、登录用户、字段偏好、导入批次和通知结果；Redis 负责新需求、状态变更、关注人变更和同步事件的可靠消费，失败事件最多重试 3 次后进入死信队列。未配置 MongoDB 或 Redis 时，本地开发可降级使用 JSON 和禁用队列，但测试、预发和生产环境必须连接真实服务。

飞书 OAuth 登录后会自动创建或更新企业用户。只有从需求方入口登录过的成员才获得需求方身份；交付管理员和超级管理员是可叠加权限，因此管理员也可以在建立需求方身份后切换到“我的需求”工作台。PM 不是全局账号角色，而是需求方提交每条需求时可选的人员字段；被指定的 PM 只看到与自己相关的需求。

## 二、已实现功能

- 需求方通过飞书 OAuth 登录、提交需求、选择多名需求人和关注人、按需指定 PM、查看与下载本人相关需求。
- 需求负责人可继续维护关注人，完成后的需求可评价；关闭评价或超过设定天数未评价时系统自动记为 5 分好评，1–3 星必须填写理由。
- 所有交付管理员均可查看完整台账；每名管理员可独立隐藏、显示、排序和筛选词条，并选择任意数量的常用词条组成个人视图。
- 超级管理员可在“管理员设置”中直接搜索飞书通讯录并任命或移除交付管理员；普通管理员不能管理他人权限，任命动作会写入审计日志。
- 需求方与管理员身份独立：只有从需求方入口完成登录的成员才获得需求方身份；管理员如需提交或关注自己的需求，需要再从需求方入口登录一次。
- 总台账、245 和高峰加入支持 `.xlsx` 预检后增量导入，并记录新增、更新、未变化和冲突数量。
- 系统读取飞书 Base 的总台账、245 和高峰加入三张业务表：Base 记录新增或修改后由自动化调用受保护的 webhook，系统约 300ms 合并同表连续事件并立即拉取对应表；服务启动和默认每 5 分钟的全表同步作为漏事件校准，也可由超级管理员手动触发。
- 只有“获取状态”发生真实变化时才进入通知队列，并通过飞书应用机器人通知需求负责人、需求人、关注人、PM，以及该需求相关且已被任命的管理员。
- 交付效率分析按 Excel 口径计算六个交付环节的 Q1/Q2 样本数、平均值、中位数、标准差、效率提升，以及预计与实际交付偏差和数据来源对比。
- `/healthz` 提供依赖状态，`/metrics` 提供 Prometheus 文本指标。

飞书 Bot 的技术链路为：NestJS 在需求提交、网页台账更新或三张飞书表同步时比较“获取状态”，仅为真实状态变化生成事件，`ioredis` 将事件写入 Redis 可靠队列；后台消费者把需求负责人、需求人、关注人和 PM 识别为需求方，把部门负责人、项目对接人、解决方案负责人和承接方责任人中已任命的管理员识别为负责管理员，通过 MongoDB 已登录用户映射或飞书通讯录 OpenAPI 得到 `open_id`，再使用 `LARK_APP_ID` 对应的“交付管线”应用机器人调用飞书 IM OpenAPI 发送个人通知。消息包含需求名称、原状态、新状态、Sprint 和系统入口；首次全量导入不发送历史状态通知，避免批量打扰。发送结果写入 MongoDB，失败最多重试 3 次，仍失败则进入 Redis 死信队列；`LARK_WEBHOOK_URL` 仅在需要额外发送群通知时配置。

## 三、功能改进与技术栈

| 功能 | 当前实现 | 技术栈 |
| --- | --- | --- |
| 三张飞书表同步与在线入口 | Base 自动化在记录新增或修改后调用系统 webhook，系统定向同步发生变化的表；启动同步和 5 分钟轮询作为兜底。管理员可直接打开三张在线表，超级管理员可手动校准。 | 飞书 Base Workflow、HTTP Webhook、NestJS 串行同步队列、飞书 Base OpenAPI、MongoDB、Redis |
| 飞书 Bot 通知 | 仅在“获取状态”真实变化时写入可靠队列，后台消费者解析需求方和负责管理员并发送飞书应用机器人消息，失败重试后进入死信队列。 | NestJS、`ioredis`、Redis、飞书通讯录与 IM OpenAPI、MongoDB 通知日志 |
| 需求方与管理员登录 | 飞书 OAuth 回调后自动创建或更新内部用户，未配置管理员角色的员工默认进入需求方页面；管理员只有从管理员入口登录时才进入对应工作台，同一账号可以同时拥有需求方能力。 | 飞书 OAuth 2.0、NestJS、签名 `HttpOnly` 会话 Cookie、MongoDB 用户表、基于 `open_id`/邮箱的角色白名单 |
| 管理员个性化词条 | 每名管理员可把词条拖入显示区或隐藏区、调整顺序，并选择任意数量的常用词条组成个人视图；前 4 个常用词条滚动时固定，偏好只对当前账号生效。 | HTML5 Drag and Drop、原生前端状态管理、CSS `position: sticky`、NestJS 偏好接口、MongoDB 按 `open_id` 持久化 |

| 个性化台账 | 每位管理员在统一台账中独立设置显示列、隐藏列、列顺序、固定列、筛选和排序，配置写入 MongoDB。 | React 页面、用户字段偏好、MongoDB |

```env
NODE_ENV=production

PUBLIC_APP_URL=https://data-panel-dev.shlab.tech

LARK_APP_ID=<飞书应用 App ID>
LARK_APP_SECRET=<通过安全渠道配置>
LARK_REDIRECT_URI=https://data-panel-dev.shlab.tech/api/auth/lark/callback
LARK_AUTH_HOST=https://open.feishu.cn
LARK_API_HOST=https://open.feishu.cn

LARK_WIKI_NODE_TOKEN=<承载台账 Base 的 Wiki 节点 token>
LARK_BASE_WEB_URL=https://aicarrier.feishu.cn/wiki/ZqC3whTTXiU2rUkLdRycTtmhnYE
LARK_LEDGER_TABLE_ID=tbl7FrAYMpseNuPA
LARK_LEDGER_VIEW_ID=vewkBG8gpp
LARK_245_TABLE_ID=tbl6dWpodWYuWNq7
LARK_245_VIEW_ID=vew41dhWuZ
LARK_GAOFENG_TABLE_ID=tbl8iFcCizgi0YrU
LARK_GAOFENG_VIEW_ID=vewkBG8gpp

LARK_DELIVERY_ADMIN_NAMES=顾语莺,高骊骏,王志,郭显淼
```

如果部署人已经取得 Base 的真实 `app_token`，可设置 `LARK_BASE_TOKEN` 并不设置 `LARK_WIKI_NODE_TOKEN`。否则服务会使用 Wiki API 自动把 `LARK_WIKI_NODE_TOKEN` 解析为 Base `app_token`。若某张表不在同一个 Base 中，可用 `LARK_LEDGER_URL`、`LARK_245_URL` 或 `LARK_GAOFENG_URL` 覆盖对应在线入口。

可选配置：

```env
SATISFACTION_AUTO_GOOD_DAYS=7
LARK_WEBHOOK_URL=<可选的群机器人 webhook>
LARK_SUPER_ADMIN_EMAILS=<超级管理员邮箱，逗号分隔>
LARK_DELIVERY_ADMIN_EMAILS=<交付管理员邮箱，逗号分隔>
```

`ADMIN_PASSWORD` 只用于 `AUTH_MOCK_ENABLED=true` 的本地开发兜底，正式环境不应开放口令管理员登录。密钥、数据库密码和真实数据不得提交到 Git。

## 五、飞书后台配置

飞书应用需要启用网页应用和机器人，并配置与 `LARK_REDIRECT_URI` 完全一致的 OAuth 重定向 URL。应用可用范围需要覆盖全部测试用户和管理员。

应用权限分为两类身份，不能互相替代。后端服务全部使用 `tenant_access_token`（应用身份），`npm run setup:lark-sync` 使用 `lark-cli` 的用户身份。

应用身份（后端运行时必需）：

| 权限 | 用途 | 对应接口 |
| --- | --- | --- |
| `auth:user.id:read` | OAuth 登录并获取当前用户身份 | `authen/v1/user_info`、`authen/v2/oauth/token` |
| `contact:contact.base:readonly` | 读取通讯录成员基本信息 | `contact/v3/users/find_by_department` |
| `contact:user.base:readonly` | 读取成员姓名与 `open_id` | `contact/v3/users/find_by_department` |
| `contact:department.base:readonly` | 读取部门树，用于通讯录选人 | `contact/v3/departments/0/children` |
| `im:message:send_as_bot` | 状态变化时发送机器人通知 | `im/v1/messages` |
| `wiki:node:read` | 把 Wiki 节点解析为 Base `app_token` | `wiki/v2/spaces/get_node` |
| `base:table:read` | 读取三张业务表的表结构与名称 | `bitable/v1/apps/{app_token}/tables` |
| `base:record:retrieve` | **读取三张业务表的记录** | `bitable/v1/apps/{app_token}/tables/{table_id}/records` |

用户身份（仅 `npm run setup:lark-sync` 需要）：`base:workflow:read`、`base:workflow:create`、`base:workflow:update`、`base:table:read`。

注意 `base:record:read` 是用户身份权限，不能替代后端 `tenant_access_token` 所需的 `base:record:retrieve`；飞书对记录读取接受 `base:record:retrieve`、`bitable:app:readonly`、`bitable:app` 三者任一，前者是新版最小权限命名。权限新增后需要发布新版本并由企业管理员审批；Base 和 Wiki 空间本身也要把该应用加入可访问范围，高级权限开启时还要确保应用角色能访问三张业务表。

用应用凭证可以直接实测每项权限是否已生效，不必依赖后台界面：

```bash
# 返回 code=0 表示该权限已开通；99991672 表示尚未开通并会列出缺失的 scope
curl -s -X POST "$LARK_API_HOST/open-apis/auth/v3/tenant_access_token/internal" \
  -H 'Content-Type: application/json' \
  -d "{\"app_id\":\"$LARK_APP_ID\",\"app_secret\":\"$LARK_APP_SECRET\"}"
curl -s -H "Authorization: Bearer <tenant_access_token>" \
  "$LARK_API_HOST/open-apis/bitable/v1/apps/<app_token>/tables/$LARK_LEDGER_TABLE_ID/records?page_size=1"
```

`/healthz` 的 `larkSyncStatus.sources[].lastError` 也会逐张表回显飞书原始报错和开通链接。

部署环境配置完 `PUBLIC_APP_URL` 和 `LARK_BASE_WEBHOOK_SECRET` 后，在具备 Base 管理权限且已登录 `lark-cli` 的管理终端执行：

```bash
npm run setup:lark-sync
```

脚本会读取三张真实数据表的名称，创建并启用“交付管线实时同步 · 总台账 / 245 / 高峰加入”三个 Workflow；重复执行时会复用同名 Workflow，不会重复创建。应用身份还需要被授予该 Base 的查看权限，否则运行时会返回 `91403`。

管理员身份可通过 open_id、企业邮箱或姓名初始化。超级管理员还可以在页面的“管理员设置”中直接从飞书通讯录任命管理员；超级管理员身份仍只通过部署环境配置。管理员只有在从需求方入口完成过登录后，才会同时拥有需求方工作台。

### 当前待解阻塞（2026-07-29 实测）

三表同步链路的代码和配置已就绪，实际跑通还差三项外部授权，全部不在代码侧：

1. **应用身份缺少 Base 记录读取权限**。`bitable/v1/apps/{app_token}/tables/{table_id}/records` 对三张表均返回 `99991672`，提示需要 `base:record:retrieve`、`bitable:app:readonly`、`bitable:app` 任一。开通入口：`https://open.feishu.cn/app/cli_aacc8ff785fadce7/auth?q=base:record:retrieve&op_from=openapi&token_type=tenant`。未开通前全量同步和实时同步都拉不到任何记录，`/healthz` 会逐张表回显该错误。
2. **执行 `setup:lark-sync` 的用户不是该 Base 的高级权限拥有者**。`lark-cli base +workflow-list` 返回 `800004011 not advanced base owner`，因此三个 Workflow 无法创建。需要由“数据团队总表”所有者把执行账号提升为高级权限管理员，或授予“可创建和启用自动化 Workflow”的权限。普通编辑权限不足。
3. **部署环境尚未配置 `LARK_BASE_WEBHOOK_SECRET`**。测试环境 `/healthz` 的 `larkSyncStatus.eventPushConfigured` 为 `false`，此时 `/api/webhooks/lark/base` 会直接返回 `503`。必须先在部署环境注入该密钥，再用同一个值执行 `npm run setup:lark-sync`，两侧不一致会返回 `401`。

已实测通过、无需再申请的能力：Wiki 节点解析为 Base `app_token`、通讯录部门树与成员读取、Base 表结构与表名读取。

## 六、发布与验证

开发阶段只推送 `dev`，由 GitLab CI/GitOps 部署到测试域名。验证 OAuth、个人需求隔离、管理员字段权限、PM 可见性、Excel 预检导入、Base 同步、飞书通知和满意度后，再将 `dev` 合并到 `main`。

部署后检查：

```bash
curl https://data-panel-dev.shlab.tech/healthz
curl https://data-panel-dev.shlab.tech/metrics
```

`/healthz` 中 MongoDB、Redis 应为 `ready`，`larkSync` 应为 `configured`。上线前还应检查应用日志中没有 OAuth 回调、Base 权限或机器人发消息错误，并确认 Redis processing 和 dead-letter 队列为空。
