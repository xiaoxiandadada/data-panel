# 数据同步架构与性能

## 数据落在哪里

**所有同步进来的数据都存在 MongoDB 里**，这一点从一开始就是这样，不需要额外改造：

| MongoDB 集合 | 内容 |
| --- | --- |
| `ledger_records` | 全部需求记录（五张飞书源表合并后的结果），每条带 `business_key` 与 `sort_order` |
| `app_state` | 数据集元信息（`meta`）、字段表（`fields`）、数据版本计数器（`version`） |
| `ledger_logs` | 字段变更审计日志 |
| `import_batches` | 每次同步 / 导入的批次摘要（新增、更新、未变化、冲突数） |
| `notification_logs` | 飞书通知发送结果 |
| `app_users` / `user_field_preferences` | 用户与个人列偏好 |
| `api_keys` | 对外 API 密钥（仅 SHA-256 摘要） |

`data/project-data.json` 只是**本地开发**在没有 MongoDB 时的回退，线上不使用（`/healthz` 的 `mongodb` 字段为 `ready` 即表示走的是 MongoDB）。

飞书那五张表是**数据来源**，不是存储：每轮同步把它们读出来、合并、写进 `ledger_records`。系统的所有读路径（网页、`/api/v1`、CSV 导出）都只读 MongoDB，不实时穿透到飞书。

## 按表同步的接口

保留并补齐了三个入口，都要求超级管理员：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `POST` | `/api/sync/lark` | 全部五张表同步一轮 |
| `POST` | `/api/sync/lark/sources/:key` | **只同步一张表**。`key` 可以是源键（`ledger` / `corpus` / `pool` / `gaofeng` / `clarify`）、飞书 tableId，或表的显示名 |
| `GET` | `/api/sync/lark/sources` | 列出五张表的配置、在线链接与各自的最近同步状态 |
| `POST` | `/api/webhooks/lark/base` | 飞书 Workflow 实时推送入口（按 `recordId` 只同步单条） |

单表同步和全量同步走同一个串行队列，不会并发互相踩。

## 同步为什么慢，以及改了什么

### 实测的耗时构成（2026-08-05 线上）

| 源表 | 记录数 | 分页数（500/页） | 本表耗时 |
| --- | --- | --- | --- |
| 待澄清项目 | 78 | 1 | — |
| 数据团队需求池 | 691 | 2 | 3.6s |
| **战略语料库获取表** | **4679** | **10** | **31.6s** |
| 高峰项目获取表 | 142 | 1 | 3.6s |
| 数据团队总表 | 648 | 2 | 6.3s |

串行累计 **45.2s**，其中语料库一张表占 **70%**。瓶颈是等飞书返回，不是本地计算。

### 三处已经改掉的浪费

1. **五张表改为并发读取**（`fetchSources`，并发上限 `LARK_SYNC_CONCURRENCY`，默认 3）。原来是串行，一轮的成本是五张表相加；现在约等于最慢那一张。按上表算约 45s → 32s。并发有上限而不是无限放开，因为飞书对 Base 读取有限流，语料库单表就是 10 个请求，无限扇出迟早触发限流，反而变成重试风暴。

2. **台账只读一次。** 原来循环里每张表都 `readDataset()` 一次，等于把 6020 条记录从 MongoDB 拉五遍。现在整轮读一次，五张表在内存里依次合并。

3. **只写变化的记录。** 原来每张表合并完都调用 `saveDataset()`，而它是 `deleteMany({})` + `insertMany(全部)` —— 一轮同步把整张表重写五遍。现在按业务键批量 upsert，只写真正变化的记录（典型一轮几十条），且**永不删除**。

   > 这一条同时修掉一个丢数据的 bug：需求方在「读快照」和「写回」之间提交的需求，会被那份旧快照整表覆盖掉，静默消失。一轮五张表就是五个窗口，每 5 分钟一轮。详见下一节。

4. **数据版本一轮只 bump 一次。** 原来每张表写完都 bump，前端 3 秒轮询发现版本变了就整份重新下载，等于一轮同步触发最多 5 次全量重下。

### 合并顺序不能动

`mergeFields` 是「非空值后写覆盖先写」，所以顺序是设计的一部分：

```
待澄清项目 → 数据团队需求池 → 战略语料库 → 高峰项目 → 数据团队总表
```

总表最后，因为它才是交付进度的权威来源。**并发只作用于「读取」，合并仍严格按上面的顺序串行进行**，所以并发不会改变任何一个字段的最终取值。

### 还能更快的地方（需要业务决策，尚未做）

语料库那 31.6s 是当前的地板，要再往下压只有三条路，都需要业务侧确认：

1. **给语料库建一个过滤视图**，只同步真正需要的行，把 `LARK_CORPUS_VIEW_ID` 指过去。4679 条里有 3442 条是已完结的自动采集线索（`数据ID` 形如 `xsk_202505000316`），如果这些不需要进系统，这张表能瘦掉一个数量级。**这一项此前就没和业务侧确认过，当前同步的是整表。**
2. **拉长全量同步间隔，靠 webhook 保实时。** 全量同步本质是兜底；飞书 Workflow 的实时推送才是主链路，它只同步单条记录，成本极低。目前 `LARK_SYNC_INTERVAL_MS=300000`（5 分钟）。**前提是先把五个 Workflow 建起来**（见部署文档，尚未完成）。
3. **增量拉取。** 飞书 Base 的 `search` 接口支持按字段过滤，如果源表有「最后修改时间」列，就能只拉变化的行。需要先确认这五张表是否都有这样一列。

## 丢数据 bug 的机制与修复

已确定性复现。原来的同步循环：

```
for 每张源表:
    incoming = 从飞书拉取           ← 几秒到三十几秒
    existing = readDataset()        ← 读
    merged   = merge(existing, incoming)
    saveDataset(merged)             ← deleteMany({}) + insertMany(全部)
```

`readDataset()` 与 `saveDataset()` 之间不是原子的。需求方在这个窗口里提交了需求，写进了库；随后同步用它那份**不含这条需求**的旧快照整表覆盖，这条需求就被删掉了 —— 页面上表现为「我加的需求，第二次登录就不见了」。

修复：同步改用 `writeChangedRecords()`，只 upsert 变化的记录、永不删除，因此无论两边如何交错，并发提交都不会丢。需求方提交侧也从「读整份台账 → 改 → 写回」改成 `insertRecord()` 只插一条，避免反向覆盖掉同步结果。

新记录的 `record_id` 由存储层在写入时分配。合并过程算出的 `import-N` 是基于它自己那份内存快照的，并发提交可能已经占用了同一个号 —— 这一点是**在真实 MongoDB 上测出来的**（唯一索引报 `E11000 duplicate key`），JSON 回退没有唯一索引，永远复现不出来。所以同步插入的新记录改用 UUID，需求方提交仍用可读的 `import-N` 但带重试。

## 网页卡顿

主因不在同步，而是**响应从来没有压缩过**：

| | 大小 |
| --- | --- |
| `/api/data?mode=admin`（6020 条 × 133 列） | **17.7 MB** |
| 同一份数据 gzip 后 | **0.32 MB** |

相差 **55 倍**。前端 JS 包（216 KB）同样是裸传。线上 `/`、`/healthz`、`/assets/*.js` 的响应头里都没有 `content-encoding`。

换算成实际下载时间：

| 网速 | 未压缩 | gzip |
| --- | --- | --- |
| 50 Mbps 办公网 | 3.0s | 0.1s |
| 10 Mbps 家宽 | 14.8s | 0.3s |
| 4 Mbps 弱网 | 37.0s | 0.7s |

已在 `src/server/main.ts` 启用 `compression`（`threshold: 1024`，避免给 3 秒一次的版本轮询那种几十字节的响应做无谓压缩）。本地实测 18523817 → 335871 字节，JS 包 217553 → 66329 字节。

**仍待处理**：管理端台账没有分页，6020 条全量渲染成约 10 万个表格单元格。压缩解决了传输，但浏览器仍要解析 17.7 MB JSON 并构建整张表。这一项单独跟进。
