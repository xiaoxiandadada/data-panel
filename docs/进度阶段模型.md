# 进度阶段模型

单一真源在 `src/server/core/progress.ts`。浏览器和对外 API 都用它，不各自维护一份状态表。

## 为什么换掉原来的映射

原来是一张扁平的 `状态 → 百分比` 表，18 个条目，命中不了就落到 `statusGroup` 的粗粒度启发式（done→100 / risk→35 / pending→15 / active→60）。

2026-08-06 在线上量到 26 个实际在用的状态，其中 **12 个不在那张表里**：`历史已入库`、`内采排队中`、`返工`、`已停滞`、`合同OA审批中`、`方案审批中`、`解决方案中`、`标注中`、`采集中`、`采购中`、`风险/异常`、`需求提出`。它们全部被报成同一个 60%，占了 1615 条进行中需求里的相当一部分。

另外两个具体的错：

- `需求取消` 被映射成 **100%**。取消的需求从来没有交付，把它算成满进度会抬高每一个它出现的平均值——线上有 231 条。
- 前端还留着自己的一份 `STATUS_PROGRESS`，已经和服务端不一致，同一条需求由谁回答会得到不同的百分比。

## 阶段划分

| key | 阶段 | 区间 | 归属状态 | 里程碑列 |
| --- | --- | --- | --- | --- |
| `intake` | 需求受理 | 3–12 | 待开始、pending、需求提出、排队中 | 需求提出时间 |
| `clarify` | 需求澄清 | 12–26 | 需求澄清中、内采排队中 | 需求澄清完成时间 |
| `solution` | 方案与审批 | 26–44 | 解决方案中、方案审批中、需求OA中、合同OA审批中 | 解决方案对接时间、解决方案对接完成时间 |
| `sourcing` | 采购与供应商 | 44–58 | 采购调研中、供应商选择中、数据采购中、采购中 | 采购反馈预报价时间、采购预报价时间、合同签订时间 |
| `production` | 数据生产 | 58–80 | 进行中、数据采集中、采集中、数据标注中、标注中、转语料库执行、返工、已停滞、风险/异常 | 开始执行时间、期望交付日期 |
| `acceptance` | 交付验收 | 80–92 | 验收中 | 实际交付完成日期、首次全量交付时间、验收通过交付量(GB) |
| `settlement` | 结算收尾 | 92–99 | 待结算 | 结算金额、结算完成时间 |
| `closed` | 已完结 | 100 | 已完结、已完成/已有、已有、历史已入库、已上线、验收通过 | — |

区间宽度是刻意不均的：`数据生产` 最宽，因为需求实际上大部分时间耗在那里；`结算收尾` 最窄，因为走到这一步基本等于交付完成。

两个专用值：

- **0%** 只属于无法量化的需求——已取消，或带着模型不认识的状态。所以阶段从 3 起，而不是 0。
- **100%** 只有 `closed` 能达到。`结算收尾` 上限停在 99，正在结算的需求永远不会和真的做完的需求报同一个数。这 1 点的缺口是有意留的。

`已停滞` 和 `返工` 放在 `数据生产` 而不是 `交付验收`：返工是把活退回生产，而把一个停滞的需求报成 88% 是这个视图里最容易误导人的数字。两者都带 flag，进度被压在所处阶段的中点，不让里程碑把它们推到阶段顶部。

## 阶段内细分

只有阶段还不够——同一个 `数据采集中` 可能刚开工也可能快交付了。阶段内位置按该阶段的**里程碑列填了几个**来定：

```
percent = start + (end - start) × (已填里程碑数 / 里程碑总数)
```

实测效果：

| 记录 | 百分比 |
| --- | --- |
| `数据采集中`，无里程碑 | 58 |
| `数据采集中` + 开始执行时间 | 69 |
| `数据采集中` + 开始执行时间 + 期望交付日期 | 80 |

没有里程碑列的阶段固定落在区间中点：我们知道它在哪个阶段，但没有证据再定位得更细，硬取任一端都是在编造精度。

`期望交付日期` 在总表里是文本列，真的会存 `最大值（待填）` 这类占位值，这种不算里程碑达成——上表第 4 种情况仍然是 69。

## 平均值的分母

`progressSummary` 的 `measured` 恒等于 `total - cancelledCount - unknownCount`，并且这三个数都单独报出来，可以手工复算。

界面上「整体交付进度」旁边必须同时写出口径，因为读者的第一反应是拿「已完结 ÷ 总数」去复算，那会得到另一个数。需求方视图的说明文案就是这么写的：

> 按 6143 / 7257 条可量化需求的交付阶段加权平均得出，而非「已完结 ÷ 总数」。不计入平均值：已取消 231、状态未设置 883。

管理端「完成度」圆环之前显示的是 `已完成/总数`，和 KPI 卡里的「完成率」是同一个数字换了个标签。现在圆环改成阶段加权平均，两个数不再重复。

## 客户端如何取到同一个数

两件事配合，缺一不可：

1. **`GET /api/progress/model`**（不需要鉴权，它是定义表，没有任何记录数据）返回完整词表：阶段区间、归属状态、里程碑列、取消状态、阻塞/返工状态、占位值正则。浏览器用它渲染阶段梯——每段的宽度、标签、颜色。
2. **每条记录自带 `progress`**，由服务端算好后附在返回的记录上，浏览器直接用这个百分比，不自己算。

第 2 点是必须的，原因很具体：需求方的数据经 `publicDataset` 收窄到 `publicFields`，而阶段细分要读的里程碑列**恰好都不在里面**——`结算金额`、`实际交付完成日期` 这类字段不该出现在需求方的浏览器里。如果让前端拿收窄后的数据去跑模型，算出来的百分比会系统性偏低：实测 `缅甸语视频` 在界面上显示 80%，同一条记录从 `/api/v1` 读出来是 88%。发送算好的数字而不是原始证据，既保证了一个需求只有一个答案，又没有扩大暴露面。

同理，`attachProgress` 必须拿**未收窄**的记录来算。它一度被放在 `publicDataset` 之后执行，于是在已经丢掉里程碑列的数据上求值，等于把同一个 bug 换了个位置。现在按 `record_id` 回查原始记录，测试里有一条专门守这个行为。

附在记录上的 `progress` 不含 `stages` 数组：阶段梯对同一阶段的所有记录都一样，逐条重复的话一个 6974 条的管理端负载要多带 5 万多个冗余对象。前端用 `stageIndex` 加已经取到的模型自行重建。

模型没取到、且记录也没带 `progress` 时，前端一律显示「未设置」并把该行标为不可量化，而不是回退到另一份可能已经漂移的表。

已验证：以线上实测的 26 个状态 × 10 组里程碑组合共 260 种输入，服务端 `progressDetail` 与仅依据序列化模型复算的结果**零差异**；需求方视图两种模式下 9 条记录的界面百分比与 `/api/v1` **逐条一致**，界面显示的 77% 可由 API 返回值手工复算得出。

## 已知的边界

- **`未设置` 占 883 条（12.2%）**，这是目前最大的一块无法量化的量。它不是模型的问题，是源表里那些行确实没有状态。`/healthz` 的 `progress.unknownCount` 往上走，就是飞书那边冒出了新状态或者漏填。
- 零宽字符污染的状态（如 `解决方案中<U+200B>`）仍能正确归入阶段，因为 `normalizeText` 会剥掉它们。存量脏值另有清洗，见部署文档。
- 新增状态需要同时更新 `progressStages` 里的 `statuses`。`tests/server-core.test.mjs` 里有一条测试把线上实测的状态清单全部跑一遍，漏了会红。
